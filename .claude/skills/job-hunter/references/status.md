This is how the live verification above was done, and it's the permanent workaround for testing fills on any page going forward without needing the user's real keyboard.
- **`category-modal.js` now identifies the actual unrecognized field unambiguously** (v0.5.10, revised v0.5.13) — the header used to show only `rawLabel`, a DOM-proximity guess (`nearestPrecedingText()` in `field-scanner.js`) that can be flatly wrong (confirmed: a language-switcher `<select>` on an InHire page surfaced labeled "Jobs", copied from an adjacent nav link, not the field itself). It now also shows a `<tag type="..." id="..." name="..." class="...">` technical descriptor — class name included because it's often the *only* clue for a custom widget with no id/name (e.g. `class="react-dropdown-select"` reveals the widget when nothing else does). v0.5.10 also added scrolling to and outlining the actual element on the page; **removed again in v0.5.13 per explicit user feedback** ("I dont need the input highlighted just need it to show on the modal if a name easy to identify") — the fix belongs entirely inside the modal's own text, not as a page-level highlight.
- **`field-scanner.js` now scopes scanning to the page's actual `<form>`** when one exists (v0.5.11) — was scanning the whole page for any `select`/`input`/etc., which caught site chrome like the InHire language-switcher above (confirmed via DOM inspection: the real name field is inside the page's one `<form>`, the language `<select>` isn't inside any form). Falls back to whole-page scanning only when the page has zero `<form>` elements at all, so form-less SPA-style ATSes aren't broken by this.
- **`field-scanner.js` now dedupes nested matches of the same widget** (v0.5.13) — the generic custom-widget selector (`role=combobox`, `class*=dropdown/select`) matched 3 nested elements of one `react-dropdown-select` instance (root container, inner `-content` trigger, `-dropdown-handle` button), so one widget was scanned as up to 3 separate unmatched fields, each popping its own near-identical modal in a row (this is what looked like "the same thing" repeating). Now only the outermost matched element per DOM cluster survives — any candidate that's a descendant of another candidate is dropped.
- **`runAutoComplete()` now guards against concurrent runs** (v0.5.12) — confirmed happening live: Claude's `run-auto-complete` debug hook and what looks like the user's own real `Ctrl+Shift+U` press landed close together on the same InHire tab, and with no guard the two runs interleaved, producing two stacked duplicate "unrecognized field" modals (`category-modal.js`'s overlay uses a fixed, non-unique DOM id, so both survived visually on top of each other). A module-level `autoCompleteInFlight` flag now makes a second concurrent call a no-op (with its own status-banner message) instead of racing. **Notably, this strongly suggests the shortcut may now actually be firing for the user** — see below.
- **The resume-attachment pipeline's `mirroredPath`-empty bug is fully fixed** (was: `resumeMeta.mirroredPath` stuck at `""` on records auto-seeded before the `chrome.downloads` race-condition fix, so every `attach-file` pending action got queued with no `filePath` at all and could never be resolved). The *recovery path itself* (`agent-bridge.js`'s `"reseed-resume"` action) was also broken — it tried to `fetch()` the bundled `seed/Manuel_Almeida_Resume.pdf` from a **content script**, which silently fails (`TypeError: Failed to fetch`) because `manifest.json` has no `web_accessible_resources` entry for it. Fixed by moving the fetch into `background.js` (`seedResumeFromBundle()`, wired as message type `job-hunter:reseed-resume`) — background scripts can always fetch their own bundled resources with no such restriction, and this also avoids adding `web_accessible_resources` at all (which would've made the resume PDF fetchable by any page that knows the extension id). `agent-bridge.js`'s `"reseed-resume"` case now just relays to background via `chrome.runtime.sendMessage`.

## Resolved this session, awaiting user confirmation

**`Ctrl+Shift+U` root cause found (2026-08-18)**: `chrome.commands.getAll()` in the background service-worker console showed `{name: "auto-complete", shortcut: ""}` — Chrome's internal command registry has **no key sequence bound at all**, despite the manifest's `suggested_key: "Ctrl+Shift+U"`. Chrome silently drops a suggested key it can't assign (most often a conflict with another extension or a reserved combo) rather than erroring, and `chrome://extensions/shortcuts` can *look* like it shows the right key while the live registration is actually empty. This is not a code bug — nothing in `background.js` or downstream could ever have fixed it. **The fix is a manual one-time rebind**: `chrome://extensions/shortcuts` → find "Job Hunter Assistant" → click into the (actually empty) input next to "Trigger JH - Auto Complete on the current page" → press the desired combo directly (try `Ctrl+Shift+U` first; if Chrome rejects it, something else already owns it — try `Ctrl+Shift+Y` or `Alt+Shift+U` instead).

**Possible sign it's now working**: later the same session, Claude's debug-hook trigger and something else landed on the same tab close together and produced a concurrency bug (two runs racing — see the `runAutoCompleteInner` guard above) that could only happen if *two separate triggers* fired `runAutoComplete()` around the same time; Claude only fired it once via the debug hook, so the second was very likely the user's own `Ctrl+Shift+U` actually reaching the content script. Not confirmed by a direct "yes it works now" from the user, though — a new session should ask directly rather than assume this circumstantial evidence settles it.
