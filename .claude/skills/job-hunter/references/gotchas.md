# Gotchas (hard-won, this session)

## Browser-automation tool limits (mcp__claude-in-chrome__*) — read this before assuming Claude can test something

These were each discovered the hard way and cost real debugging time. **Claude cannot:**

- **Navigate to `chrome://*` or `chrome-extension://*` URLs.** The `navigate` tool unconditionally prepends `https://` to anything that doesn't already start with `http://`/`https://`, producing a malformed `https://chrome-extension://...` URL that errors. This is why the whole `agent-bridge.js` postMessage-relay design exists: Claude reaches this extension's storage from *any regular page* it's already on, never by visiting the options page directly.
- **See or click the browser's own toolbar/address bar/extension-icon tray.** `computer{action:"screenshot"}` only captures the page's content viewport — confirmed by testing (a Google.com screenshot showed zero browser chrome, starting from y=0 with page content). This means Claude cannot click the extension's toolbar icon, and cannot use it to discover the extension's ID that way either — the ID has to come from the user (`chrome://extensions`, the 32-char string under the extension name) or be read off a `chrome-extension://...` URL already visible in `tabs_context_mcp`'s tab list.
- **Open or interact with Chrome's real native right-click context menu.** A `computer{action:"right_click"}` only dispatches a synthetic `contextmenu` DOM event to the page (which a page's own JS could hook for a *custom* menu) — it does NOT invoke Chrome's actual native menu, confirmed by screenshotting immediately after and seeing no menu rendered. So Claude cannot test/use "JH - Draft email with resume" or "JH - Message with resume" itself either — only the user can click those.
- **Dispatch a real OS-level keyboard shortcut that `chrome.commands.onCommand` would catch.** Extension commands are handled by Chrome's browser-chrome input layer, above the page — a CDP-injected key event aimed at page content doesn't reach it. This is why the `Ctrl+Shift+U` auto-complete trigger (see status.md) couldn't be fully diagnosed by Claude alone this session.

**What Claude *can* do to test things anyway**: navigate to ordinary `http(s)://` pages, run arbitrary JS there via `javascript_tool` (main-world execution — see the isolated-world note below), and use the `agent-bridge.js` postMessage protocol to read/write extension storage from any such page. When something needs the toolbar/context-menu/shortcut specifically, that has to be a "please test this yourself and report back" ask to the user — don't burn turns guessing.

## "Create group" means the Claude-in-Chrome MCP tab group, not a native Chrome tab group

When the user says "create group" (this project's shorthand for a `job-hunter`-labeled Chrome tab group), don't assume it's unreachable just because native right-click "Add tab to group" is off-limits (see the context-menu bullet above) — the **Claude in Chrome extension itself** holds real `chrome.tabGroups` permission for the tabs it drives, separate from what page-level automation can reach:

- Call `mcp__claude-in-chrome__tabs_context_mcp` with `createIfEmpty: true`. This creates/returns the session's own MCP tab group (a `tabGroupId`), no native-UI interaction needed.
- The group's visible **label is auto-derived from the current CCD session's title**, not settable through any `claude-in-chrome` tool parameter. To get it labeled `job-hunter`, rename the session itself: `mcp__ccd_session_mgmt__set_session_title({session_id: "self", title: "job-hunter"})`.
- Whether renaming the session updates an *already-created* group's label live, or only takes effect for a group created after the rename, wasn't confirmed as of 2026-08-18 — `computer{action:"screenshot"}` can't see the tab strip (per the bullet above) so Claude can't verify the label itself; ask the user to look and report back.

## Isolated world vs. main world — the reason agent-bridge.js exists at all

`mcp__claude-in-chrome__javascript_tool` executes code in the page's **main world** (same JS realm as the page's own scripts). Content scripts (everything under `extension/content/` and `extension/shared/`) run in the extension's **isolated world** — a separate global object (`self`/`window`) that main-world code cannot see into, and vice versa. Concretely: `typeof JH` evaluated via `javascript_tool` is **always** `"undefined"`, even when every content script loaded correctly and `self.JH` is fully populated inside them — this is not a bug, it's the security boundary working as designed. (This tripped Claude up mid-session: an `await`-less async IIFE plus this exact confusion briefly looked like "content scripts aren't loading" when they actually were — the real test is a `window.postMessage` round-trip through `agent-bridge.js`, which crosses the isolated/main-world boundary by design, not a direct `JH` reference.)

The only two channels that cross this boundary: `window.postMessage` (what `agent-bridge.js` uses), and the DOM itself (both worlds see and can manipulate the same live document — which is how `selector-fill.js`'s fill functions work, called from *within* the isolated world, not from `javascript_tool`).

## Chrome extension `commands` key-binding syntax is stricter than it looks

Tried, in order, and all three of the first two failed at manifest-load time with "Invalid value for 'commands[1].default'": bare `"F9"`, then `"Alt+F9"`. Bare function keys are not a valid `suggested_key.default` on their own, and `Alt+F9` specifically wasn't accepted either. What's confirmed to load successfully: `"Ctrl+Shift+U"` — the standard `Ctrl+Shift+<letter>` pattern used in Chrome's own extension samples. **Don't hand-guess this syntax again** — if a different key combo is wanted, verify the exact accepted grammar rather than trying variations against the user's real Chrome (each failed guess costs them a reload cycle). Even with a manifest-valid binding, Chrome can *silently* leave a `suggested_key` unassigned if it conflicts with something else — always double-check `chrome://extensions/shortcuts` shows the expected key next to the expected command, don't assume a clean manifest load means it's actually bound.

## The `chrome.downloads` race condition (mirroredPath silently empty)

`background.js`'s `mirrorBlobToDisk()` originally called `chrome.downloads.download(...)` then immediately `chrome.downloads.search({id})` to read the resolved file path. The `download()` callback only confirms the download **started**, not finished — for the read-immediately-after pattern, `filename` frequently comes back as `""` because the file hasn't finished writing yet. Fixed by waiting for `chrome.downloads.onChanged` to report `state.current === "complete"` (or `"interrupted"`, which now rejects) before reading the path. Any future code that mirrors a blob to disk must follow the same wait-for-completion pattern — don't reintroduce the immediate-read version.

## The salary-field masking bug (why every text fill is now char-by-char)

A real GrupoBolt/InHire salary field (`#salaryExpectation`, `inputmode="decimal"`) uses JS-driven formatting that reads keystrokes incrementally. Setting `.value = "15000"` in one bulk assignment (via the native setter + a single `input` event) made the field's own logic misread the whole string as an unformatted 7-digit number and render **R$1.500.000,00** (1.5 million) instead of the intended **R$15.000,00** — a silent, wrong-by-100x value, not a visible failure. Fixed by `simulateTyping()`: set the value incrementally, one character at a time, dispatching a real `InputEvent` after each character with a small delay — this is now the *only* path for single-line text fields (not conditionally applied only to "known masked" fields), since it's harmless on unmasked fields and there's no reliable way to detect "is this masked" up front anyway.

## `mcp__claude-in-chrome__file_upload` can't read the `mirroredPath` directly — copy to scratchpad first

`resumeMeta.mirroredPath` (from `background.js`'s `chrome.downloads` mirror) is an absolute path like `C:\Users\...\Downloads\job-hunter\current-resume.pdf`. Passing that straight to `file_upload`'s `paths` fails: **"only files this session is allowed to read can be uploaded"** — the tool is sandboxed to the session's own working/output/attachments/uploads folders (or folders the user explicitly connected), not arbitrary filesystem paths, even ones Claude's own `Read`/`Bash` tools can freely access. Two ways to resolve a real `attach-file` pending action, in order of preference:
1. **Copy the file into the session's scratchpad directory** (`cp` via Bash), then pass *that* path to `file_upload`. Cheap, works for any file size up to the tool's 10MB cap.
2. `file_upload` also accepts inline `files: [{name, mimeType, data}]` (base64) instead of `paths` — but **don't** read the file through `Read` to get that base64 first: reading a ~120KB PDF as base64 text burns on the order of 150K+ tokens and gets truncated by the context-window cap before you even finish reading it. Only use this path if the file is very small, or you already have the base64 from a source that didn't require dumping the whole thing into context.

## Real ATS DOM quirks encountered (useful priors for the next new site)

- **GrupoBolt / InHire** (`*.inhire.app`): `#name`, `#email`, `#linkedinUsername`, `#salaryExpectation`, `input[name=resume]` (type=file). Phone country picker is a `react-dropdown-select` widget (`.react-dropdown-select-content` trigger, opens a `[placeholder="Search the country"]` search input + `.react-dropdown-select-item` results) — confirmed exactly one instance per page, so that selector is safe to use directly if ever needed as a fallback, though the generic `discoverComboSearchWidgets()` DOM-diffing approach handles it without any hardcoded selector now.
- **GeekHunter**: `aria-label`-driven signatures ("Nome completo", "Email", "Confirmar Email", "LinkedIn"), a `name="resume"` file input that's `hidden` by default (custom "Attach resume" button shows instead — confirms `field-scanner.js`'s deliberate choice to never visibility-filter file inputs), and **two separate salary fields** per posting: `salaryExpectation.CLT` (formal employment) and `salaryExpectation.PJ` (contractor) — both currently resolve to the same `compensation.salary_floor_brl_monthly` value (a known, documented simplification, not a bug).
- Both sites confirm the underlying premise of the whole category-matching rework: "name"/"nome", "email", "linkedin", "resume"/"cv"/"currículo", "salary"/"salário" recur near-identically across unrelated ATS vendors — the dictionary genuinely generalizes rather than needing per-site tuning.

## `javascript_tool` output redaction

Some field values come back as `"[BLOCKED: Sensitive key]"` or `"[BLOCKED: Cookie/query string data]"` — this is the tool's own output-sanitization layer redacting suspected-sensitive content (seen on `work_authorization` and on raw `outerHTML` dumps containing certain attribute patterns), not a real data-loss issue in the extension. Don't treat a redacted field as evidence of a bug in `storage-schema.js` — re-query a narrower expression (e.g. specific sub-fields instead of a full object dump) if the actual value is needed for debugging.

## Never leave a raw `{{placeholder}}` in a resolved draft-email/message-profile action

A `draft-email` or `message-profile` pending action's `subject`/`body` can still contain unresolved `{{...}}` tokens when `JH.scrapePageContext()` didn't find that field on the original page (e.g. `{{recruiter_name}}`, `{{role_title}}` — `template-engine.js` leaves an unmatched placeholder as the literal brace text rather than blanking it). User explicitly corrected this (2026-08-21) after a draft went out reading "Hi {{recruiter_name}}," and "Application | {{role_title}}". Before creating the Gmail draft (or LinkedIn DM), reword around any missing value instead of passing the brace syntax through:
- Missing `recruiter_name` in a greeting → drop it (`"Hi {{recruiter_name}},"` → `"Hi,"`), don't invent a name.
- Missing `role_title` → user's specified default is **"Software Engineer position"** — use it both as the subject line and inline in the body (`"interested in the {{role_title}} position at X"` → `"interested in the Software Engineer position at X"`).
- This is a stopgap at draft-time, not a fix for the underlying scrape/template-fill gap on that page — worth a separate note if it keeps happening on one site.

**Also include salary expectation** (user requirement, 2026-08-21): every `draft-email`/`message-profile` body should state a salary expectation, even though `message-template.seed.json`'s body has no `{{salary}}` placeholder for it — add it as an explicit line when resolving the pending action. Compute it from `candidateData.compensation` per its own `rule` field: use the higher of the applicable currency floor (`salary_floor_usd_monthly`/`_brl_monthly`/`_eur_monthly` — USD for English/Spanish job posts, BRL for Portuguese, EUR for Euro-denominated) or the top of any range stated in the job post, choosing currency by the job post's language/company as described in that `rule` string. **If the job post's language/currency can't be determined, default to USD** (`salary_floor_usd_monthly`) rather than guessing another currency.

## Resume storage can silently corrupt to the literal text `"[object Object]"`

Confirmed 2026-08-21: both the disk-mirrored copy (`chrome.downloads`-mirrored path from `resumeMeta.mirroredPath`) and the IndexedDB blob (`STORE_RESUME_BLOB`, what `"job-hunter:get-resume-base64"` reads) contained the literal 15-byte string `"[object Object]"` instead of real PDF bytes — despite `resumeMeta` itself looking healthy (real `fileName`, real `mirroredAt`). Root cause per the Blob constructor spec: `new Blob([arrayBuffer], {type: "application/pdf"})` in `background.js`'s `handleSaveResume` will silently stringify `arrayBuffer` via `String()` if it isn't actually a real `ArrayBuffer`/typed array at that point — producing exactly this string, with no thrown error anywhere in the chain. Not yet root-caused *which* call path handed it a non-`ArrayBuffer` (the normal `options.js` file-input flow does `file.arrayBuffer()` correctly; suspect an earlier session's `agent-bridge.js` `"relay-to-background"` call for `job-hunter:save-resume` passed a JSON-serialized array/object instead of a structured-cloned `ArrayBuffer`).
**Don't trust `resumeMeta` alone as proof the resume is attachable.** Before relying on either resume source, verify the byte count/PDF header (`%PDF-`) — a real resume PDF is >50KB; 15 bytes of `"[object Object]"` is the exact corruption signature. **Workaround used successfully**: skip the extension's storage entirely and read the real PDF straight from wherever the user keeps it on disk (e.g. `~/Downloads/<fileName from resumeMeta>.pdf`), copy it into the session's scratchpad, and attach it via `mcp__claude-in-chrome__file_upload` on Gmail's own compose UI (see the `create_draft` base64-cost gotcha below) rather than through `create_draft`'s inline-base64 `attachments`.

## `mcp__claude_ai_Gmail__create_draft`'s inline-base64 attachment is too expensive for a real resume — use Gmail's own compose UI instead

`create_draft` only accepts attachments as inline base64 `content`, no file-path option. Reading a ~130KB PDF and base64-encoding it (`[Convert]::ToBase64String(...)` or similar) produces ~176K characters of base64 text — `Read`-ing that back into context to use as the tool-call argument cost **168K+ tokens for just the first 22K characters (12.6%) of the file**, before hitting the `Read` tool's own 25000-token-per-call cap; the full file would need ~8 chained `Read` calls and over 1M tokens total. Don't do this for any real attachment-sized file. Instead, drive Gmail's own compose UI directly: click Compose, fill To/Subject/Body via `computer`, then use `find` to locate the (hidden) `<input type="file">` in the compose window and `mcp__claude-in-chrome__file_upload` with a local path — the file goes straight from disk into the browser without its bytes ever passing through Claude's context. Closing the compose window (not clicking Send) auto-saves it as a draft, same end result as `create_draft` would have given, at a fraction of the cost. `create_draft`/`update_draft` are still the right tool for attachment-free drafts or for verifying a draft's final state afterward (`list_drafts` with `DRAFT_VIEW_FULL`).
